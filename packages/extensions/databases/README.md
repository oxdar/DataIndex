# dataindex-ext-databases

An independently installable DataIndex extension for SQLite. It indexes
allowlisted table, column, primary-key and foreign-key metadata, then performs
bounded live reads using host-approved typed query definitions.

## Install

```powershell
python -m pip install dataindex-core
python -m pip install dataindex-ext-databases
```

The extension uses Python's standard-library `sqlite3` module and adds no
runtime parser or database-driver dependencies. PostgreSQL, views, virtual
tables, arbitrary SQL and schema migration are not supported.

## Authorization and query safety

The host authorizes the database source before registering it and passes its
explicit local path to `SQLiteDatabaseExtension.register_database`. The
extension never derives a path from a source ID. Registration requires a
per-source table/column allowlist and one or more immutable `QueryDefinition`
objects. Tool requests name only an approved query ID and supply values for its
declared filters; they cannot supply SQL, table names, columns, operators or
join expressions.
For registered sources, `tools_for_source()` also publishes the approved query
IDs as a schema enum so a planner can discover valid operations without
guessing. The central DataIndex dispatcher still validates the request and
rechecks source authorization before execution.

Every connection uses SQLite URI `mode=ro`, enables `query_only`, disables
trusted schema, applies an SQLite authorizer, and has bounded lock and value
limits. Query values are bound parameters. Joins must match an allowlisted
single-column declared foreign key; composite-FK joins are rejected. Only
`COUNT` and `SUM` aggregates are available. Results are bounded to at most 100
rows, 32 selected columns, 64 KiB of serialized row data, and 100,000 SQLite
virtual-machine instructions, with an additional cooperative deadline from the
caller. Reads and schema checks run within one SQLite read transaction.

For shared multi-tenant databases, the host must include a
`FixedFilterRule` for each required source/tenant scope in every approved query.
These predicates are generated by the host and are combined with caller filters;
the tool request cannot override or omit them. This is a query-level scope
control, not a replacement for host authorization or database/file permissions.

The extension indexes no table rows. Schema records contain only allowlisted
table/column metadata and foreign-key nodes that point to their target table
node. Live query evidence includes the source ID/version, query ID, read
timestamp, schema version, canonical request filters, effective limit, query
definition digest, database file-state digest, result rows, truncation status
and operation. Aggregates are marked as calculated evidence; monetary example
values use integer cents to avoid floating-point totals.

The host must use an immutable snapshot identifier as `SourceRef.version`.
Registration and reads detect ordinary changes to the main database and WAL
file identity (device, inode, size and modification time), but this metadata
digest is not a content hash and cannot prove that a file's bytes were not
rewritten while preserving those attributes. Up to 256 source revisions can be
registered at once; registering a new revision does not evict earlier ones.

The caller remains responsible for source authorization, protected file
permissions, and selecting a source path. Read-only SQLite mode is
defense-in-depth, not a substitute for OS-level access controls or the central
DataIndex dispatcher.

### Hosts that persist the configuration

`register_database_config(source, database_path, config)` registers a database
from a JSON-compatible configuration with exactly two keys: `allowed_columns`
(table name to column names) and `queries` (1 to 128 `QueryDefinition.to_mapping()`
values, validated through `QueryDefinition.from_mapping`). A host can store that
form and register the source again after a restart; the DataIndex local mode
does this for `submit_database`. `database_source_version(path)` returns a
`sqlite-state:` version string for the file's current main-database/WAL state,
and `unregister_database(source_id)` drops every registered revision of a source
and returns how many were dropped. A configuration with other keys, or an invalid
definition, raises `InvalidDatabaseConfigurationError`.

## Example

Run [`examples/basic_usage.py`](examples/basic_usage.py) from a source checkout.
It creates a temporary synthetic contracts/invoices database, registers only
approved schema and queries, then prints schema locators and cited aggregate
evidence. The SQL fixture is synthetic and contains no production data.
